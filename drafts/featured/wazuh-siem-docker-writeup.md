# Wazuh SIEM on Docker — with VirusTotal, AbuseIPDB & ChatGPT Integration

A self-hosted SIEM lab built from scratch on Docker, with three threat-intel/AI integrations wired into the alert pipeline and verified end-to-end against a live Windows agent.

**Stack:** Wazuh 4.9.0 (Manager, Indexer, Dashboard) · Docker Compose · Ubuntu 24.04 LTS host · Windows 11 agent

---

## Deployment

Used the official `wazuh-docker` repository (single-node setup) rather than a manual package install, for a clean and reproducible environment:

```bash
git clone https://github.com/wazuh/wazuh-docker.git -b v4.9.0 --depth=1
cd wazuh-docker/single-node
docker compose -f generate-indexer-certs.yml run --rm generator
docker compose up -d
```

This pulled the manager, indexer, and dashboard images, generated the internal SSL certificates, and brought all three containers up. Confirmed with:

```bash
docker ps
```

All three (`wazuh.manager`, `wazuh.indexer`, `wazuh.dashboard`) showed `Up`. Logged into the dashboard over HTTPS and had a clean install with every default module available — Endpoint Security, Threat Intelligence, MITRE ATT&CK, Vulnerability Detection.

Connected a Windows 11 PC as an agent using the install command generated by the dashboard's **Deploy new agent** wizard, pointed at the manager's IP on port 1514. It showed up as **Active** in the Endpoints Summary within seconds of installing.

## Problem 1 — config changes kept disappearing after every restart

The first real issue came up while adding the VirusTotal integration. `ossec.conf` was edited directly inside the running container with `docker exec`, and `docker restart` was run to apply it — but every time, the change was gone, reverted back to the original file.

The cause: in `docker-compose.yml`, the manager service mounts a host file into the container at a *staging* path, not directly onto `ossec.conf`:

```yaml
- ./config/wazuh_cluster/wazuh_manager.conf:/wazuh-config-mount/etc/ossec.conf
```

On every startup, an internal script copies that mounted file over the real `/var/ossec/etc/ossec.conf` — so any edit made directly inside the container gets silently overwritten on the next restart. The fix was to always edit the actual source file on the host, `config/wazuh_cluster/wazuh_manager.conf`, and let the container copy it in on restart — not edit the file inside the container at all.

---

## Problem 2 — `wazuh-db` and `wazuh-integratord` failing with a generic XML error

After moving to editing the correct file, both `wazuh-db` and `wazuh-integratord` started throwing:

```
ERROR: (1226): Error reading XML file 'etc/ossec.conf': (line 0)
```

`xmllint --noout` on the file pointed to the real cause: two separate `<ossec_config>` root blocks in the same file (left over from how the default config is structured, plus a duplicate introduced while editing). Wazuh's own config reader doesn't reject that — the built-in daemons handled it fine — but `wazuh-db` and `wazuh-integratord` specifically choked on it and refused to start.

Fixed by merging everything into a single `<ossec_config>...</ossec_config>` block and validating with `xmllint --noout` before every restart from then on:

```bash
xmllint --noout config/wazuh_cluster/wazuh_manager.conf
docker restart single-node-wazuh.manager-1
```

Even after that fix, a stale state persisted until the container's data volumes were wiped and recreated fresh:

```bash
docker compose down -v
docker compose up -d
```

After that, `wazuh-control status` showed every daemon running clean (`analysisd`, `remoted`, `syscheckd`, `wazuh-db`, `wazuh-integratord`, etc.).

## VirusTotal integration

Wazuh has native support for VirusTotal, so this only needed an API key added to `ossec.conf`:

```xml
<integration>
  <name>virustotal</name>
  <api_key>YOUR_API_KEY</api_key>
  <group>syscheck</group>
  <alert_format>json</alert_format>
</integration>
```

Scoped to the `syscheck` group, meaning it fires on File Integrity Monitoring (FIM) alerts — whenever a monitored file is created, modified, or deleted.

**Test:** created a file inside a real-time-monitored directory on the Windows agent (the `Startup` folder, which is the only path in the default FIM config with real-time watching enabled). Within seconds, Wazuh had hashed the file and sent it to VirusTotal automatically:

```json
{"virustotal": {"found": 0, "malicious": 0, "source": {"file": "...test-fim.txt", "md5": "...", "sha1": "..."}}, "integration": "virustotal"}
```

`found: 0, malicious: 0` — expected, since it was a harmless test file. Confirmed in the dashboard's dedicated VirusTotal module as well, which listed the scanned file with a total of 1 scan and 0 malicious detections.

## AbuseIPDB integration (custom)

No built-in support in Wazuh, so this required writing a Python integration script from scratch. Wazuh calls integration scripts with the alert file path and the API key as arguments, so the script just needs to read the alert JSON, pull out an IP, and call the external API:

```python
#!/var/ossec/framework/python/bin/python3

import json
import sys
import time
import ssl
import certifi
from urllib.request import Request, urlopen
from urllib.error import HTTPError, URLError

alert_file_location = sys.argv[1]
apikey = sys.argv[2]

LOG_FILE = '/var/ossec/logs/integrations.log'

def log(msg):
    with open(LOG_FILE, "a") as f:
        f.write(time.strftime("%Y/%m/%d %H:%M:%S") + " custom-abuseipdb: " + msg + "\n")

def extract_ip(alert):
    data = alert.get("data", {})
    for key in ("srcip", "src_ip", "source_ip"):
        if key in data:
            return data[key]
    return alert.get("data", {}).get("win", {}).get("eventdata", {}).get("ipAddress")

def main():
    with open(alert_file_location) as f:
        alert = json.load(f)

    ip = extract_ip(alert)
    if not ip:
        log("No IP address found in alert, skipping.")
        sys.exit(0)

    req = Request(
        f"https://api.abuseipdb.com/api/v2/check?ipAddress={ip}&maxAgeInDays=90",
        headers={"Key": apikey, "Accept": "application/json"},
        method="GET"
    )

    ctx = ssl.create_default_context(cafile=certifi.where())
    with urlopen(req, timeout=15, context=ctx) as resp:
        result = json.loads(resp.read().decode())

    data = result.get("data", {})
    output = {
        "integration": "custom-abuseipdb",
        "abuseipdb": {
            "ip": ip,
            "abuseConfidenceScore": data.get("abuseConfidenceScore"),
            "totalReports": data.get("totalReports"),
            "countryCode": data.get("countryCode"),
            "isp": data.get("isp")
        }
    }
    log(json.dumps(output))

if __name__ == "__main__":
    main()
```

Registered in `ossec.conf`, scoped a bit wider since IP-related alerts can come from several rule groups:

```xml
<integration>
  <name>custom-abuseipdb</name>
  <api_key>YOUR_API_KEY</api_key>
  <group>syscheck,authentication_failed,web,attacks</group>
  <alert_format>json</alert_format>
</integration>
```

### Problem 3 — custom script refused to run at all

Deploying the script into the container and restarting produced:

```
ERROR: At wpopenv(): file 'integrations/custom-abuseipdb' has write permissions.
```

Comparing against the built-in `virustotal` script's file ownership (`root:wazuh`) versus the custom script's ownership (`wazuh:wazuh`, since it was copied in as the `wazuh` user) revealed the cause: Wazuh's integration daemon refuses to execute any integration script that isn't owned by `root`, as a safety measure against the `wazuh` service user modifying its own executed scripts. Fixed by matching the built-in scripts exactly:

```bash
docker exec -u root single-node-wazuh.manager-1 chown root:wazuh /var/ossec/integrations/custom-abuseipdb
docker exec -u root single-node-wazuh.manager-1 chmod 750 /var/ossec/integrations/custom-abuseipdb
```

**Test:** triggered a failed Windows login attempt (wrong password), which generated an alert containing a source IP. AbuseIPDB returned a real reputation lookup for it:

```
custom-abuseipdb: {"integration": "custom-abuseipdb", "abuseipdb": {"ip": "127.0.0.1", "abuseConfidenceScore": 0, "totalReports": 118, "countryCode": null, "isp": null}}
```

Confirmed the integration correctly pulls IPs out of alerts, queries the live AbuseIPDB API, and logs a structured reputation result — `abuseConfidenceScore: 0` was expected here since the test IP was localhost, not a real external address.

## ChatGPT integration (custom)

Same integration pattern as AbuseIPDB, but sending the alert's rule description and log details to OpenAI's Chat Completions API and asking for a short plain-language explanation plus a suggested action — aimed at speeding up alert triage for a junior analyst:

```python
#!/var/ossec/framework/python/bin/python3

import json
import sys
import time
import ssl
import certifi
from urllib.request import Request, urlopen
from urllib.error import HTTPError, URLError

alert_file_location = sys.argv[1]
apikey = sys.argv[2]

LOG_FILE = '/var/ossec/logs/integrations.log'

def log(msg):
    with open(LOG_FILE, "a") as f:
        f.write(time.strftime("%Y/%m/%d %H:%M:%S") + " custom-chatgpt: " + msg + "\n")

def main():
    with open(alert_file_location) as f:
        alert = json.load(f)

    rule_desc = alert.get("rule", {}).get("description", "No description")
    rule_level = alert.get("rule", {}).get("level", "N/A")
    agent_name = alert.get("agent", {}).get("name", "unknown")
    full_log = alert.get("full_log", "")

    prompt = (
        "You are a SOC analyst assistant. Explain this security alert in 2-3 simple sentences "
        "and suggest one recommended action.\n\n"
        f"Agent: {agent_name}\nRule level: {rule_level}\n"
        f"Description: {rule_desc}\nDetails: {full_log}"
    )

    body = json.dumps({
        "model": "gpt-4o-mini",
        "messages": [{"role": "user", "content": prompt}],
        "max_tokens": 200
    }).encode("utf-8")

    req = Request(
        "https://api.openai.com/v1/chat/completions",
        data=body,
        headers={"Content-Type": "application/json", "Authorization": f"Bearer {apikey}"},
        method="POST"
    )

    ctx = ssl.create_default_context(cafile=certifi.where())
    with urlopen(req, timeout=15, context=ctx) as resp:
        result = json.loads(resp.read().decode())
        explanation = result["choices"][0]["message"]["content"].strip()

    output = {
        "integration": "custom-chatgpt",
        "chatgpt": {
            "agent": agent_name,
            "rule_description": rule_desc,
            "ai_explanation": explanation
        }
    }
    log(json.dumps(output))

if __name__ == "__main__":
    main()
```

### Problem 4 — SSL certificate verification failure

With ownership and permissions already fixed (same `root:wazuh` / `750` pattern learned from the AbuseIPDB issue), running the script still failed:

```
URL ERROR: [SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed: unable to get local issuer certificate
```

The container's default Python SSL context didn't have a usable root certificate bundle for verifying `api.openai.com`. Fixed by explicitly loading Python's `certifi` CA bundle instead of relying on the system default — this is the `ssl.create_default_context(cafile=certifi.where())` line in both custom scripts above.

**Test:** with the fix applied and a real OpenAI API key in place, the script successfully authenticated and reached the API — confirmed by getting back a proper structured JSON error rather than a connection or SSL failure:

```json
{"error": {"message": "You have no credits remaining. Add credits to continue using the API...", "type": "insufficient_quota", "code": "credit_balance_exhausted"}}
```

This confirms the integration itself is fully working end-to-end (alert parsing → prompt building → authenticated API call → response handling) — the only thing stopping a live text response is the OpenAI account having no billing method attached, which is an account-level limitation rather than a fault in the integration.
